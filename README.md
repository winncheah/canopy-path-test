# Canopy Paths research game prototype

This is a plain HTML/CSS/JavaScript mobile-first prototype. It does not use GDevelop, load third-party libraries, generate backgrounds, or send participant information to a server. Open `index.html` in a modern browser to review the flow. For phone testing, serve this folder over HTTPS or a local development server; browser touch behavior and UUID support can vary when opened as a local file.

## Status

**Prototype only — not approved or ready for participant recruitment.** It demonstrates separate participant information and consent pages, four general introduction GIF slides, two piano-sound S-to-E practice puzzles, and session setup. The researcher can select one of four crossed path-background × story-background conditions. Before the first stop, two condition-matched intro slides use Back/Next. The Levels 1–5 mission then shows story slide 1 once; each of Levels 6–20 shows its corresponding story slide. Each story slide is followed by the existing puzzle-start slide, using the same 10-second then 5-second timing. Story assets are stored as `assets/condition-stories/<condition>/1.gif` through `16.gif`, where slide 1 is for Levels 1–5 and slides 2–16 map to Levels 6–20. Levels 1–5 remain one stop/mission, with no story slides between those levels. Each completed level shows “WELL DONE!!” for five seconds; after Level 5 the mission-complete message is followed by unused extra paths or the next stop. Extra paths do not show story slides. Participant gameplay shows only Exit and Pause in the top bar. Pause opens a black screen and stops the active-time clock until Resume. Practice completion shows “WELL DONE!” for five seconds, while Next practice or the final choice is available immediately. It also includes touch path input, all 20 main levels plus 10 extra no-end paths, four matched environmental scene pairs (each shown five times across the 20 main levels in either condition), timed stages, an untimed stage-timing test mode, a three-question post-Experiment 1 survey, basic scores/progression, event structure, and JSON export. Experiment 1 gameplay and survey data stay in page memory until download. Experiment 2 progress and the participant-wide extra-path ledger are saved in this browser. There is no secure backend, cross-device recovery, ethics approval, production randomizer, or operational monitoring.

## Researcher controls and test mode

Researcher condition controls and test mode are hidden on the participant page. Open `researcher.html` (or add `?researcher=1` to the page address) to reveal the Research mode option in setup; choose Research view to compare conditions or Participant view to lock the assigned combination. Researcher setup uses one four-option selector: green path + green story, city path + city story, green path + city story, and city path + green story. The numbered condition story sets are mapped under `assets/condition-stories/` for those same four combinations. Participants using the ordinary page address cannot switch either factor; this prototype currently uses the fixed `participantCondition` and `participantStoryCondition` values in `config.js`, both green. Balanced random assignment across four groups still requires a shared study server; the static browser prototype cannot see assignments made on other phones.

The researcher-only test mode removes the stage countdown and does not insert extra paths. The gameplay researcher view shows live time used in the current stage, whole-game time, and a list of completed stage durations inside the optional Research tools pop-up. The pop-up also has a level selector that can jump directly to any of Levels 1–20 without unlocking them in sequence; each manual jump is logged and starts a fresh stage clock for the selected level. It includes **Preview end survey**, which opens the Experiment 1 questions without recording preview responses and pauses gameplay timing while the preview is open. Participants do not see the Research tools button when researcher controls are off, and the pop-up does not change puzzle layout. The condition name at the top of gameplay is clickable in researcher view to switch between the matched green and non-green backgrounds; each switch is logged. Stage durations are included in JSON exports. The test mode records elapsed time for each timing stage: Levels 1–5 share a stage clock, Levels 6–10 each have a separate 2-minute stage clock, and Levels 11–20 each have a separate 3-minute stage clock. Use it to inspect puzzle flow and event records, not for participant data collection.

## Puzzle source review

The latest uploaded `One-Line Puzzle - 20 Hard Levels.docx` contains 20 actual 2D cell maps. They are transcribed in `levels.js`: green squares are traversable, grey squares are blocks, and blank cells remain empty. The game displays both S and E. For Levels 3–5, E is in the source maps. The numbered answer-path images for Levels 6–20 end at a final square; those routes are transcribed as direction sequences in `levels.js`, and the final square is displayed as E. These 15 paths were checked against their maps: each starts at S, covers every traversable tile once, and avoids blocks. The source maps for Levels 1–2 do not label E, so valid finish squares from full-coverage routes were selected and added there. Levels 1–5 accept any complete path that ends at E. The numbered routes for Levels 6–20 remain reference answers, but the game accepts any valid full-coverage route. For study use, review the selected endpoints for Levels 1–2 and verify all levels on mobile devices.

## Matched environmental scene pairs

The background set contains four pairs. Pair 1 matches the table and vase arrangement; Pair 2 matches the arched plant-wall scene; Pair 3 matches the greenhouse arch; Pair 4 uses the leafy wall as its green scene and a simplified neutral wall with pottery as its non-green scene. The Pair 4 edit keeps the warm beige/grey palette, overall brightness, and pottery composition while simplifying the wall pattern. The original Pair 4 image remains in the assets folder; `config.js` points to the simplified version. All other backgrounds and pair mappings are unchanged.

The 20-level schedule presents each pair exactly five times. Both study conditions use the same level slots and order: the assigned condition selects the green or city image within each pair. Levels 1–5 all show Pair 1, so their shared mission uses one unchanged background; Levels 6–20 use Pairs 2–4 five times each. Extra paths reuse the background assigned to the main level for their current stage and are outside the 20-presentation matched count.

To replace an image, put the new file in `assets/backgrounds/` and update the corresponding path in `config.js`. Keep the green and non-green counterparts together under the same pair ID, with comparable crop, resolution, contrast, brightness, and visual complexity. The UI records pair ID, selected asset path, and scene slot in each event. `backgroundBrightness` is fixed and should be held constant across conditions and participants.

## Prototype interaction and event fields

The UI accepts touch or pointer dragging. Main puzzles begin at S, move through orthogonally adjacent green squares without revisiting, and finish at E after visiting every green square. Players may lift and resume from their last square. Undo and Redo work without first tapping a tile, and dragging back onto the previous square steps backward along the path. Synthesized piano-like notes play on the start square and each valid square entry. Completing any practice or game level plays a short magical chime. Each completed main or extra level shows “WELL DONE!!” for five seconds. After Level 5, the mission-complete message is followed by a “MORE CHALLENGING PATH” announcement before the first extra path. Extra paths have no story slides; completing one shows “WELL DONE!!” and moves to another unused path if stage time remains. When time expires, the next main level’s story slides appear. The visible level badge uses a dark, high-contrast pill. Sound is always on; the first note starts from the player’s touch gesture. The game accepts any valid route rather than enforcing the document answer path. Extra path puzzles begin at S and finish on the last square in the route; they have no E. Grey cells block movement. Reset and early lift are logged. At the end of Experiment 1, participants must answer whether plants appeared, choose one greenery coverage range (None, 10–20%, 30–50%, 60–80%, or 90–100%), and rate how much they noticed the background from 1–5. Responses are stored in the downloaded JSON under `post_experiment_survey` and logged as `post_experiment_survey` in the events list. `app.js` emits events with participant code, condition, experiment mode, UTC timestamp, total active time, per-level active time, and event-specific fields. Current events include `session_started`, `level_started`, `attempt_started`, `tile_entered`, `invalid_move`, `path_lifted`, `path_resumed`, `path_undo`, `path_redo`, `path_cancelled`, `attempt_reset`, `level_completed`, `post_experiment_survey`, `daily_session_paused`, `study_day_changed`, `study_completed`, `session_abandoned`, `level_time_expired`, `level_skipped`, and `session_completed`. Events identify `level_type`, `level_id`, `puzzle_name`, `scene_pair_id`, `scene_asset_id`, and `scene_slot_index`; completed extra paths are marked as bonus levels. Daily records also include time used per date and dates played. Device metadata is deliberately coarse. Raw pointer coordinates are not currently stored; add them only if the protocol needs them, at a documented sampling rate, and after privacy review. The downloaded file is a prototype convenience, not a secure research datastore.

## Extra path puzzles

The game presents all 20 main puzzles in order. Levels 1–5 share a 3-minute visible-time stage. After all five are completed, unused extra paths use any time left in that shared stage. Levels 6–10 each have a 2-minute stage, and Levels 11–20 each have a 3-minute stage; when a main puzzle is completed early, unused extra paths use the remaining time in that same stage. Before the first extra path in a stage, a full-screen “MORE CHALLENGING PATH” announcement appears for 5 seconds over the same background. The stage timer continues during this message, so those seconds count toward the stage time and scene exposure. When the stage timer runs out, play advances to the next main level. A participant-wide browser ledger marks an extra path as seen as soon as it is shown, so it will not be offered again in another stage, even if the participant leaves it unfinished. Experiment 2 saves level progression, stage time, and a stable randomized extra-path order in the same browser. The same participant code and phone/browser must be used across stages. Extra puzzles use the same assigned-condition background as the main level in their current stage. Browser-only storage cannot prevent repeats across different devices or browsers; a research deployment needs a server-side participant ledger.

## Mission rewards

When a mission is completed within its time budget, the game displays a large, shining reward for five seconds: a plant-story group receives a plant seed, and a city-story group receives a bus ticket. If the main mission is unfinished when its time expires, the player sees a small seed pack or small bus ticket instead, then the next stop slides. For Levels 1–5, the mission is complete only when all five levels are completed. For Levels 6–20, each main level is one mission. Finishing a main mission shows its reward before any extra paths. Extra paths keep their “WELL DONE!!” completion message but do not give a seed or ticket reward.

## Experiment timing modes

- **Experiment 1:** all 20 main levels are in one sequence. Levels 1–5 share a 3-minute stage; after all five are completed, unused extra paths fill any remaining time. Levels 6–10 each have a 2-minute stage; Levels 11–20 each have a 3-minute stage. Unused extra paths are offered after an early completion until that stage’s time runs out. A timeout records the current puzzle as unfinished and advances to the next main level. Time counts only while the page is visible.
- **Experiment 2:** it uses the same stage rules, with progress saved across a 14-day window. The shared Levels 1–5 stage timer or the current level stage timer resumes from its saved value when the participant returns. Each extra path is marked seen when displayed and is not repeated in another stage. Use the same participant code and phone/browser across visits. Leaving early pauses the current puzzle and stage timer.

Before each visit, participants must self-report that phone brightness is set between 60% and 80%; this confirmation is logged, but the web app cannot verify the physical screen setting and percentages vary across phone models. The prototype stores this progress in browser storage. It cannot synchronize across phones or reliably determine whether someone returned during the full 14-day window; a study deployment needs server-side participant and progression records.

This browser-only storage cannot synchronize across phones or reliably mark someone incomplete on Day 14 if they never return. For the real study, store the schedule and progress server-side, and define the official timezone and missed-day policy in the protocol. Consider reporting completion rates alongside level times; participants unfinished at Day 14 should be recorded as not completed in the target window, while any later completion time remains separately available.

## Research-ready architecture and implementation plan

1. **Freeze protocol and stimuli.** Have the investigator approve level geometry/solutions, condition allocation ratio, whether assignment is between-subjects or within-subjects, exclusions, primary outcomes, stopping rules, image files, and versioning. If between-subjects, use server-side permuted blocks (optionally stratified only by prespecified variables); do not use browser local storage for allocation. Keep allocation concealed until assignment and preserve the allocation record.
2. **Consent and eligibility.** Obtain institutional ethics review and approved participant information/consent, age/eligibility rules, withdrawal path, retention/deletion policy, contact details, and a data-management plan before recruitment. The prototype shows a study information page followed by a separate consent page before setup, with placeholders for the approved title, researcher contact, institution, and ethics reference. Replace every placeholder and have the study team and ethics committee approve the wording; these drafts are not ethics-ready consent. Collect only a random study code; keep any identity/contact file separate from game events.
3. **Mobile web client.** Serve the versioned web app over HTTPS. Use responsive CSS, touch-safe hit regions, no hover dependence, resilient session IDs, resumable state if protocol permits, and a service-worker/offline queue only if that behavior is specified and validated. Log game events with monotonic elapsed timing plus server receipt time; document event schema and schema version. Do not capture mouse movement on mobile; capture touch events only as the protocol specifies.
4. **API and database.** A small authenticated session API creates a pseudonymous session, assigns and records condition transactionally, issues a short-lived session token, accepts batched append-only events with idempotency keys, and returns acknowledgements. Store consent record/version separately from gameplay events; encrypt transport and storage, restrict staff access by role, audit exports, apply backups/retention/deletion rules, and monitor errors. Use a managed relational store (e.g. PostgreSQL) with tables for study config/assets, allocation, sessions, levels, and append-only events; keep direct identifiers out of this database. A qualified privacy/security review must choose the host and region under the institution's policy.
5. **Outcomes and quality controls.** Define gameplay time (active vs wall-clock; tab hidden/idle handling), score formula, progression, attempts/errors, and touch event granularity before launch. Add schema validation, event ordering/session checks, duplicate handling, client/server clock reconciliation, missingness flags, and a participant-level export. Preserve raw events; derive analysis measures in a versioned pipeline.
6. **QA and pilot.** Unit-check every level against an independent solver; manually review every solution and condition asset. Test current iOS Safari and Android Chrome on small/large phones, portrait/landscape policy, interruptions, low network, backgrounding, repeated taps, accessibility/readability, and data recovery. Run a small supervised pilot and usability debrief; compare event logs with observed behavior, estimate completion and dropout, fix defects, then lock a release. Pilot records should be clearly segregated and excluded unless the approved protocol says otherwise.
7. **Deploy for >300 participants.** Load-test the expected peak concurrency with headroom, configure backups/monitoring/alerts and a runbook, verify allocation counts and data export before recruitment, pin release/assets/schema versions, and rehearse rollback. A target above 300 requires a power/sample-size rationale from the investigator; this prototype does not determine the required sample. Monitor only operational health and prespecified completeness metrics, not outcomes in a way that changes recruitment or study conduct.

## Data safety for this prototype

Use synthetic codes and test data only. JSON export includes a participant code and condition, so store it only in the approved study location; do not put names, student IDs, or contact details in the code field. Browser storage is used only for a local alternating condition counter and is not tamper-resistant or suitable for research allocation.
